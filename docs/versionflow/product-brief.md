# VersionFlow · 产品案例与 MVP 边界

> 资料基线：用户提供的 VersionFlow 归档（2026-10-09）；本文件为产品作品集摘要，并非插件完整技术规格。  
> 当前状态：**嘉立创 EDA 专业版上的实验性可运行插件，v0.0.5**。真实用户需求及生产级可靠性尚未验证。

## 01. 用户场景与产品判断

当 PCB 工程被多次修改时，设计者需要知道某个器件发生了什么位置变化。最初愿景曾涵盖版本可视化、对象增删改、高亮定位以及 BOM/采购/生产影响提示，但这些不能通过一天的 MVP 可信交付。

因此首期被收敛为**版本快照 → 手动 Checkpoint → 按位号查询器件位移**。核心问题是：在嘉立创 EDA 中，不依赖私有版本 API，能否让一个器件在多次提交中保持身份一致、查到完整轨迹，并在重启后恢复？

## 02. 范围冻结

**现阶段用户可以：**

1. 在嘉立创 EDA 专业版中导入 VersionFlow 0.0.5。
2. 对真实 PCB 执行读取探针，获取有位号、内部 ID、x/y 坐标的组件记录。
3. 创建 Initial Baseline，之后分别移动同一器件并手动提交 Checkpoint 1、Checkpoint 2。
4. 输入器件位号 R1，查到从 Baseline 到 Checkpoint 2 的两段位移。
5. 重启 EDA 后再次检索，已提交历史保持一致。

**当前不提供：**自动监听页面变化、实时版本树、设计版本回滚、对象级完整语义 Diff、PCB 画布差异高亮或点击定位、BOM/生产影响计算、多窗口事务一致性。技术 Spike 中曾验证原始对象快照与 Raw Diff，但不等于 v0.0.5 的运行时产品能力。

## 03. 技术取舍的产品含义

| 设计决策 | 为什么这样做 | 限制 |
| --- | --- | --- |
| 插件自己存储 Checkpoint | 避免依赖公开接口之外的原生历史管理能力 | 不是 EDA 原生版本树，需用户手动提交 |
| 只关注元件位置 | 快速验证「变化能被查到」这一单一价值假设 | 不代表电气、制造等其他设计变更 |
| 以内部器件 ID 追踪 | 避免同位号、改名或重建引发错误串联 | 缺失 ID 或同位号多实体需明确歧义 |
| 失败不得推进历史 | 用户必须能信任前一已提交版本仍然可用 | 真实存储失败只做了离线模拟 |
| 验证单窗口 | 当前 Web Locks 降级方案未保证跨窗口提交原子性 | 不能宣传多窗口并发支持 |

**产品方法论**：先识别最小技术可验证单元，再选择用户操作流程；不要在真实 EDA 读取尚未通过时先铺大型 UI。

## 04. 技术 Spike 与实机验证

较早的 Technical Spike 通过桥接接口验证源读取、规范化、对象级比较和差异识别，并观察过包含 129 个底层文档对象的样例结构；这是**研究阶段的独立技术探索**，不代表最终 v0.0.5 运行时对 129 个真实器件做了轨迹追踪。

最终 v0.0.5 在嘉立创 EDA 专业版 3.2.203、Windows 环境中，以测试项目 \`test / PCB1\` 的 **R1 一项真实器件**完成三次状态记录：

| 历史节点 | X | Y | 与前一次记录差值 |
| --- | ---: | ---: | --- |
| Initial Baseline | 48615 | 83585 | — |
| Checkpoint 1 | 63365 | 90330 | +14750, +6745 |
| Checkpoint 2 | 53675 | 92645 | -9690, +2315 |

实机证据包括 Baseline 成功、两个 Checkpoint 提交、Trace 查询与重启后一致记录。完整验收结果见 [acceptance.md](./acceptance.md)。

## 05. 评测结论：已验证 vs 未验证

| 等级 | 结果 |
| --- | --- |
| EDA 实机已验证 | 扩展菜单加载、文档读取、Baseline、CP1/CP2、R1 两段轨迹、重启恢复 |
| EDA 实机已验证（限定场景） | 重复 Baseline 拒绝，历史不推进 |
| 离线模拟验证 | 存储写入失败后历史不推进、部分同位号/并发冲突、不同格式解析 |
| 未验证 | 跨 EDA 窗口并发真实提交、存储硬失败实机、真实用户效率与需求价值 |
| 未实现 | 完整 Visual History、工艺/采购影响、自动 Diff 可视化、一键定位等 |

## 06. 产品复盘与下一阶段决策门槛

下一阶段应先开展真实工程师访谈：记录他们目前如何追查 PCB 修改、会频繁查询哪些变化、手动 Checkpoint 是否增加负担。将 Stage B 基准实验和正常操作流程对照，测量**查找指定器件位移所需时间、失败率及用户对结果的信任度**，再决定是否扩展至其它设计对象和可视化版本树。

**本项目当前不宣称**提升某百分比生产效率、已经降低制造事故、或解决 BOM 影响分析问题。
